## TASK 21 — Gmail sender authentication (final remediation, Review 1.3 follow-up)

- Investigation: the IMAP provider already fetches the whole message (`BODY.PEEK[]`) but the pipeline never read `Authentication-Results`; every inbound `from_address` was trusted as stored. Recipient pinning (TASK 03) guaranteed that the address a human approved is the only one a send may use, but not that the sender is genuine.
- Evidence rules (`app/services/sender_authentication.py`, pure and fail-closed): only the TOPMOST `Authentication-Results` header is read (for mail delivered by SMTP the receiving server prepends its own, so an attacker-supplied header travels BELOW it); its authserv-id must be EXACTLY `mx.google.com` (no dot stripping, no extra tokens); credit requires exactly one `dmarc=pass` result with exactly one `header.from` whose validated ASCII domain (one root dot allowed; internationalized domains are NOT converted because IDNA 2003 and 2008 disagree, so such a sender stays unverified) equals the domain of the stored From address, and exactly ONE `From` header on the message; only INBOUND mail is credited. The header is read with a bounded tokenizer honouring quoted strings and nested/escaped comments (text inside them is never a result); `spf=pass` / `dkim=pass` alone are never credited; missing, malformed (`pass-fail`, spaced `=`, unbalanced quotes/comments, a clause without `method=result`), ambiguous or malformed property sequences (two dmarc clauses, two `header.from`, a stray `=`, `header . from`, an empty value), oversized, control-character or injected-line-break headers => `UNVERIFIED`; explicit `dmarc=fail` => `FAILED`. Folded headers (CRLF + whitespace) are unfolded first.
- Trust boundary (a limit, not a proof): nothing inside a message can prove that Google wrote the topmost header. A party able to WRITE into the mailbox (IMAP APPEND, an import tool, the Gmail API insert call) can place a forged first header and obtain `DMARC_ALIGNED`. That is mailbox compromise, the same accepted class as the full-access App Password in CLAUDE.md; it is documented, not defended. Ordinary SMTP forgery is not credited (the forged header sits below Google's own, or the From domain does not align).
- Statement of meaning: `DMARC_ALIGNED` proves the DOMAIN of the From address authorised the mail. It does NOT prove who the person is or that the display name is genuine.
- Storage: `gmail_messages.sender_auth` (migration `c5d8f1a3b7e2`, nullable, CHECK on the three values), written once at insert, never upgraded; NULL (every existing row) reads as unverified. The raw header is not stored, so history is not re-evaluated.
- Policy (decided with Codex review below): FAIL CLOSED. `POST /response-drafts/{id}/decision` with `APPROVED` and the send path both refuse (409, no write, provider never called) unless the message's `sender_auth == DMARC_ALIGNED`; a REJECTED decision stays possible; the operator answers an unverified sender manually after verifying it by another channel. `GET /response-drafts/{id}/state` returns `sender_authentication` and a visible `sender_warning`. Recipient pinning from TASK 03 is unchanged and still enforced.
- Consequence for operations: replies to recruiters whose mail is not DMARC-aligned in Gmail's header (some ATS relays) cannot be approved/sent from this system. That is intentional. Existing approvals are already unsendable (empty pin, TASK 03).

## TASK 23 — Multi-worker sessions and rate limiting (final remediation, Review 2.4/AUD-004 follow-up)

- Inventory of process-local state: 19 rate limiters (`_RateLimiter`, incl. the failed-authentication budget and the UI login limiter), the UI logout revocations, and the per-process cookie nonce. - Atomicity: PostgreSQL takes a transaction-scoped advisory lock per (limiter, identity) and then runs ONE conditional `INSERT ... SELECT ... WHERE count < max`; SQLite relies on that single statement under its write lock. Refund deletes exactly the reserved row AND only for the same client (the table is `AUTOINCREMENT` on SQLite, so a delayed refund token can never match a newer reservation). Cost, counted per operation and excluding commits: one limiter check of a KNOWN client is 3 statements on SQLite / 4 on PostgreSQL (own cleanup, count, insert; PostgreSQL +1 advisory lock); of a NEW client 5 / 6 (the live-cap and storage counts are added); a complete authenticated API request in shared mode (generic check + failed-auth reserve + refund) is about 9 statements for a known client and 13 for a new one on SQLite, and 2 more on PostgreSQL; the periodic cleanup adds up to 40 batches of one statement every 30 s per process and limiter.
