### HARD-005 — `_ShutdownRequested` (scheduler SIGTERM handling) could be silently swallowed mid-cycle
- **Priority:** P2 · **Verified/Theoretical:** VERIFIED · **File/function:** `app/scheduler.py::_ShutdownRequested`, `_handle_sigterm`
- **Reproduction:** `tests/test_scheduler_poll_loop.py::TestShutdownRequestedPropagatesThroughTickLevelExceptionHandling` (2 tests) — raises `_ShutdownRequested` from inside the faked `run_due_cycle_if_claimed`, asserts it propagates out of `_poll_loop` uncaught (not logged as `automation_scheduler_poll_iteration_error`), and asserts the class hierarchy directly (`not issubclass(_ShutdownRequested, Exception)` / `issubclass(_ShutdownRequested, BaseException)`).
- **Impact:** `_ShutdownRequested` (added in the prior `chore/production-readiness-r1` branch to fix AUD-008) subclassed `Exception`. A SIGTERM landing while control was inside `_poll_loop`'s own per-tick `try: ... except Exception:` block (wrapping `run_due_cycle_if_claimed`/`run_due_digest_if_claimed`) would have been silently caught there and misreported as a generic tick error, with the poll loop continuing instead of shutting down — meaning a single `docker stop` could occasionally be absorbed and ignored, requiring a second signal (or an eventual SIGKILL after the orchestrator's grace period) to actually stop the container.
- **Fix status:** **FIXED.** `_ShutdownRequested` now subclasses `BaseException` directly, deliberately mirroring `KeyboardInterrupt`/`SystemExit` — the exact same reasoning the standard library uses for those two.

**VERIFICATION PASS — design-safety re-analysis (not just the swallowing fix above).** The original test only proved `except Exception` no longer swallows the shutdown signal — necessary but not sufficient to prove the overall design is safe against interruption at an *arbitrary* point inside an active cycle (mid-commit, mid-CAS-update, mid-collector-call, mid-heartbeat-cleanup). A dedicated trace was performed:

- **Architecture compared:** (A) current — signal handler raises `BaseException` immediately, interruptible at any interpreter-level "tick" (PEP 475: a blocking syscall with a Python signal handler registered is interrupted rather than silently retried on `EINTR`, well-defined CPython behavior, not exotic). (B) alternative — a cooperative flag/`asyncio.Event` checked only at chosen safe points. B was NOT implemented: it would either (i) only check between poll-loop ticks, giving *worse*, unbounded shutdown latency for a SIGTERM landing mid-cycle (the exact scenario this finding is about), or (ii) require threading cancellation checks through `run_automation_cycle`'s business/orchestration logic, which is a business-workflow redesign explicitly out of scope for this session.
- **Key safety invariant identified:** the DB is the sole source of durable truth in this codebase's design, not in-process Python state — every write this trace examined (lease claim, CAS update, run-completion commit) is a single atomic DB-level operation; an async-raised exception can only ever land *before* such a commit (nothing durable happens, `_poll_loop`'s `finally: db.close()` rolls back any pending transaction — confirmed by SQLAlchemy's standard `Session.close()` behavior) or *after* it (the DB is already durably correct regardless of what the Python-level exception does next). This is the SAME invariant the lease/CAS crash-recovery design already has to guarantee for a literal SIGKILL, which gives ZERO chance to run any Python cleanup at all — an async-raised `BaseException` is strictly gentler, since `finally` blocks do get a chance to run.
- **Heartbeat thread lifecycle checked directly (not assumed):** read `_RunLeaseHeartbeat.stop()` (`app/services/automation.py`) — it calls `self._thread.join(timeout=self._interval_seconds + 1.0)`, a bounded but real join that waits for the heartbeat's current DB operation (on its own, separate `Session`) to finish before returning. This property is NOT specific to `_ShutdownRequested` — it already has to hold for `run_automation_cycle`'s `finally: heartbeat.stop()` to be safe under ANY exception type unwinding through it, so `_ShutdownRequested` introduces no new class of risk here.
- **New test added:** `tests/test_automation_lease.py::TestShutdownRequestedDuringActiveCycleCleansUpSafely` — raises `_ShutdownRequested` from inside a REAL `run_automation_cycle` call (not a poll-loop-level fake, one layer deeper than the existing HARD-005 test), with a REAL heartbeat thread running, against a real SQLite-file-backed engine. Proves, concretely: (1) no `automation-run-lease-heartbeat` thread is left alive after the call unwinds (`threading.enumerate()` check), (2) the `Session` remains usable afterward (a trivial query doesn't itself raise), (3) the abandoned `AutomationRunRecord` is left exactly `RUNNING` (not corrupted), and (4) a subsequent replacement worker, after the lease naturally expires, recovers it to `FAILED` via the SAME existing reconciliation path `TestStaleRunIsReconciledAndRecovered`/`TestReplacementWorkerAfterLeaseLoss` already prove — re-confirmed here for this specific interruption cause rather than assumed by analogy.
- **What this does NOT prove:** formal, CPython-internals-level certainty that literally every conceivable bytecode boundary is safe (e.g. an undiscovered interaction deep inside a C-extension driver's own signal handling) — that is out of reach for any test-based or code-reading analysis in this session.

**HARD-005 verdict: SAFE AS IMPLEMENTED.** Chosen over "UNCERTAIN — CODEX REQUIRED" because the trace above identifies the concrete, load-bearing safety invariant this codebase's architecture actually depends on (DB durability + `finally`-based cleanup, not in-memory Python state), demonstrates no code path where interruption produces a WORSE outcome than the SIGKILL this design already has to tolerate, and now has a passing test exercising the real, deepest-available integration point (a real `run_automation_cycle` + a real heartbeat thread). This is distinguished explicitly from HARD-008, which — despite also being "shutdown/crash-adjacent" — involves the codebase's one truly irreversible external effect (a sent email) and remains REQUIRES CODEX/ASTRA; HARD-005's worst-case outcome (an automation run retried on the next interval, no data loss, no double effect) is a categorically lower-stakes failure mode.
- **Codex/Astra:** No — mechanical fix, narrow, exactly mirrors an established stdlib pattern; verification trace + concrete test found no unsafe path, distinguished explicitly from HARD-008's genuine outbound-safety stakes.

### HARD-007 — `upsert_job`'s new-record path has no `IntegrityError` handling, unlike every sibling insert-race site
- **Priority:** P2 · **Verified/Theoretical:** VERIFIED, now on **real PostgreSQL** (upgraded from SQLite-only this verification pass) · **File/function:** `app/db/repositories.py::upsert_job` / `_finalize_job_write`
- **Reproduction (SQLite, original):** `tests/test_repository.py::test_concurrent_insert_of_the_same_new_job_can_raise_unhandled_integrity_error` — two real threads/sessions racing to `upsert_job` the exact same brand-new fingerprint against a real SQLite file-backed engine (`check_same_thread=False`); asserts exactly one thread succeeds, exactly one gets an unhandled exception, and the DB never ends up with two rows for the same fingerprint.
- **Reproduction (real PostgreSQL, added this verification pass):** `tests/integration/test_upsert_job_postgres_concurrency.py` — two tests against a disposable `postgres:16` container migrated via the real Alembic chain. A plain outer `threading.Barrier` was tried first and found **unreliable** against real PostgreSQL round-trip timing (on some runs one thread's full SELECT→INSERT→COMMIT completed before the other's SELECT even ran, so no race occurred at all — a real but uninteresting result). Fixed by injecting a SECOND barrier at the exact `get_job_by_fingerprint` read point (via monkeypatching the bare module-level name, not touching `upsert_job`'s own code), guaranteeing both threads observe `existing is None` before either proceeds to INSERT — confirmed deterministic across 5 consecutive runs. A real bug in the test itself was also caught and fixed while developing this: the cleanup fixture originally filtered on `JobRecord.fingerprint LIKE '%marker%'`, but `fingerprint` is a SHA-256 hash that can never contain a literal marker substring — the delete silently matched nothing, and a leftover row from a prior run turned the "brand-new fingerprint" race into a false-negative "already exists" non-race. Fixed to filter on `title` instead; exactly the class of test-quality issue this hardening pass's own Phase 18 looks for, caught by dogfooding this same verification pass rather than by a separate review.
- **Exact losing outcome, now confirmed on real PostgreSQL:** the loser receives `sqlalchemy.exc.IntegrityError` wrapping `psycopg.errors.UniqueViolation` naming `uq_jobs_fingerprint` explicitly — a clean, recognizable error, not an opaque driver-level surprise. A SEPARATE, PostgreSQL-specific behavior was also confirmed directly (does not reproduce on SQLite): after the `IntegrityError`, the losing `Session`'s underlying transaction is POISONED — PostgreSQL refuses every further statement ("current transaction is aborted") until an explicit `rollback()`, confirmed by a trivial `SELECT` raising before rollback and succeeding after. After that explicit rollback, the Session is fully usable again, including for a genuinely new, unrelated `upsert_job()` call, which succeeds normally — the caller is not permanently stuck, but `upsert_job` itself does not perform this rollback, so an unaware caller reusing the same Session without first rolling back would find EVERY subsequent statement on it failing too.
- **Impact:** `JobRecord.fingerprint` **does** have a DB-level `UNIQUE` constraint (`uq_jobs_fingerprint`) — data integrity is never actually violated, on either dialect. But unlike every other insert-race site in this project (`get_or_create_schedule`, `create_approval`, `claim_send_attempt`, `upsert_message`), the losing thread's `_finalize_job_write`'s `db.commit()` has no `try/except IntegrityError` — the loser gets an **unhandled, ugly 500-class failure** (e.g. two automation cycles for different accounts, or a manual run racing the scheduler, discovering the same new posting simultaneously) instead of the graceful "someone else already inserted it, use their row" resolution this project uses everywhere else it has the same race shape. On PostgreSQL specifically, an unaware caller that catches the `IntegrityError` but doesn't roll back before continuing to use the same `Session` would see every subsequent operation on it fail too, compounding the failure.
- **Fix status:** **DOCUMENTED, NOT FIXED.** A fix (catch `IntegrityError`, `rollback()`, re-read, return the winner's row) would touch `upsert_job`'s write/retry semantics — explicitly out of scope for this session's "no retry/idempotency guarantees without explicit evidence" / "stop and document" constraint, despite the fix direction being fairly obvious and now backed by dialect-specific evidence for exactly what it needs to handle (including the mandatory `rollback()` step for PostgreSQL).
- **CI:** the new PostgreSQL test is wired into `.github/workflows/ci.yml`'s existing `scheduler-postgres` job.
- **Codex/Astra:** **Codex: YES.** Astra: No (data integrity is never at risk on either dialect; this is a robustness/UX gap, not a safety-critical outbound-effect gap).

### HARD-009 — Job-fingerprint dedup has no Unicode canonicalization (NFC/NFD collision-miss)
- **Priority:** P2 · **Verified/Theoretical:** VERIFIED · **File/function:** `app/db/repositories.py::_fingerprint`

### HARD-011 — No `connect_timeout` on the DB engine: a real outage hung requests indefinitely instead of failing fast
- **Priority:** P1 · **Verified/Theoretical:** VERIFIED (live Docker experiment) · **File/function:** `app/db/session.py`
- **Reproduction — live, not simulated:** started a disposable `postgres:16` container, confirmed a healthy connection, then `docker stop`'d it and attempted a query through the SAME SQLAlchemy engine/pool. **Before the fix:** the attempt hung past 60+ seconds with no application-level bound (the test script itself had to be killed). Repeated the experiment starting a live `uvicorn` process against the same setup: `GET /api/v1/health` correctly still returned `200` (confirms AUD-002's existing finding), but `GET /api/v1/jobs` (a real DB-touching route) hung past 30 seconds with no response. **After the fix:** the same stopped-DB experiment failed cleanly with `psycopg.errors.ConnectionTimeout` — see the dual-stack nuance below. Automated regression: `tests/test_db_session_connect_args.py` (3 tests) proves the pure `_connect_args_for(url)` helper returns the right `connect_args` per dialect.
- **Impact:** a DB outage (container stopped, network partition, host down but port/network path still reachable at the OS/container level rather than actively refusing) left every DB-touching request thread hung indefinitely — no timeout, no error, no log line — rather than failing fast with a diagnosable error. Combined with AUD-002 (`/health` staying `200`), this made a real outage look like a "frozen but healthy" service from the outside: health checks pass, but no actual request ever completes or errors.
- **Fix status:** **FIXED**, with an honestly-documented nuance: `_connect_args_for` now returns `{"connect_timeout": 10}` for non-SQLite URLs (SQLite is unaffected — `{"check_same_thread": False}` as before). Re-running the exact same live stop/reconnect experiment after the fix: the failure now takes **~20 seconds, not 10** — libpq/psycopg apply `connect_timeout` **per resolved address**, and `localhost` resolves to both an IPv6 and an IPv4 address, so a dual-stack host pays the timeout twice sequentially. This is still a massive improvement (bounded ~20s vs. unbounded 60s+), but the code comment and this report both state the real, measured behavior rather than claiming an exact "10 second" guarantee. `pool_pre_ping=True` (from the prior branch's AUD-007 fix) was also re-confirmed live in this same experiment: after restarting the stopped container, a query through the SAME engine/pool (not a new engine) transparently recovered without raising a stale-connection error.
- **Dialect-safety verification (this pass):** `connect_timeout` is a psycopg/libpq-specific connection parameter, not a generic SQLAlchemy one — passing it unconditionally to the non-SQLite `else` branch is only safe if PostgreSQL is genuinely the only other dialect this project ever configures. Checked directly rather than assumed: `pyproject.toml` declares exactly one non-SQLite DB driver extra (`postgres = ["psycopg[binary]>=3.1"]`; grepped the full dependency list — no MySQL/MariaDB/other driver anywhere); `.env.example` documents exactly two `DATABASE_URL` schemes (`sqlite:///...` and `postgresql+psycopg://...`); `compose.yaml`/`docs/DEPLOYMENT.md` explicitly restrict the production compose target to PostgreSQL only ("do not use SQLite in production compose"). **Confirmed: the project's contract is SQLite (dev/test) + PostgreSQL (production) only** — no generic/other-dialect support is implied or documented anywhere. Per that confirmed contract, the implementation is kept as-is (an explicit `elif "postgresql" in url` branch was considered but not added, since the task's own guidance was to document-and-keep when the two-dialect contract is confirmed, not to add speculative dialect-detection code for a dialect that doesn't exist in this project). The reasoning is now recorded directly in `app/db/session.py`'s code comment, not just this report, so a future reader isn't left to re-derive it.
- **Codex/Astra:** No — additive engine-configuration bound, no schema/business-logic change, doesn't alter retry semantics (there is no retry here, just a bound on how long a connection ATTEMPT can take); dialect assumption now explicitly verified and documented, not implicit.

## Additional confirmed findings (documented only, no fix — lower priority or genuinely out of scope)

### HARD-012 — Skill-name matching drops the NFKC normalization step candidate-profile persistence already applies

### HARD-013 — Two functions named `normalize_company_name` with materially different normalization rules

### HARD-014 — Company Research's `record_failed_attempt` is a read-modify-write with no CAS
- **Priority:** P3 · **Verified/Theoretical:** THEORETICAL
- **File/function:** `app/db/repositories.py::record_failed_attempt` (`existing.last_attempt_at = now; ...; db.commit()`, no version check)
- **Impact:** two concurrent failed-attempt recorders racing on the same row is a last-write-wins scenario — benign in practice since only attempt-metadata (`last_attempt_at`, `attempt_count`, `last_error`) is touched, never `research_status` or research content itself.
- **Fix status:** DOCUMENTED, NOT FIXED — genuinely low priority, real fix would add a CAS layer for a benign race.
- **Codex/Astra:** No.

### HARD-015 — Rate limiting runs AFTER API-key auth, so invalid-key requests are unlimited
- **Priority:** P2 · **Verified/Theoretical:** VERIFIED (static proof — every one of ~50 routes' `dependencies=[Depends(require_api_key), Depends(enforce_*_rate_limit)]` lists was grepped and confirmed to declare auth first, consistently, with zero exceptions)
- **File/function:** `app/api/routes.py` (all rate-limited route decorators)
- **Impact:** FastAPI resolves a `dependencies=[...]` list sequentially and stops at the first exception — since `require_api_key` always comes first, a request with a wrong/missing `X-API-Key` never reaches the rate limiter at all. An attacker can brute-force the API key at unlimited request rate; only requests that already pass the key check consume rate-limit quota.
- **Fix status:** DOCUMENTED, NOT FIXED — reordering dependencies is a security-relevant behavior change (changes what gets rate-limited and when); explicitly out of this session's safe-fix scope.
- **Codex/Astra:** Codex: YES. Astra: No — API-key brute-forcing is already mitigated by the key's length/entropy being the operator's responsibility (documented in `docs/SECURITY_MODEL.md`), not a send/approval-safety-critical gap.

### HARD-016 — Automation-run lease expiry uses wall-clock time (inherent, not a code defect)
- **Priority:** P3 · **Verified/Theoretical:** THEORETICAL
- **File/function:** `app/db/automation_repository.py::_is_lease_expired`, `AUTOMATION_RUN_LEASE_TTL_SECONDS`
- **Impact:** a large forward host-clock step (NTP correction, VM pause/resume) could make a live lease appear expired early, letting a second process reclaim it while the first is still genuinely running. This is architecturally necessary — the lease must be comparable across process restarts and hosts, which a monotonic clock (reset on restart, not comparable cross-process) cannot provide — and mirrors the identical, deliberate design already used for the Gmail thread lock in the same codebase.
- **Fix status:** DOCUMENTED, NOT FIXED (and not clearly fixable without a fundamentally different locking primitive, e.g. an external coordination service, which is out of scope for this project's single-server target). Recorded so it's a known, accepted tradeoff rather than a silent assumption.
- **Codex/Astra:** No — inherent to wall-clock leases generally, not a fixable code defect.

### Phase 3 — Resource-exhaustion audit
Full inventory of every module-level mutable collection in `app/` and every DB table's growth/retention behavior. ### Phase 4 — HTTP input hardening
Full inventory of every POST/PATCH endpoint's Pydantic model bounds. Confirmed: **no application-level or server-level HTTP body size limit exists anywhere** (no Starlette size-limiting middleware, no uvicorn flag, no reverse-proxy layer in `compose.yaml`) — relies entirely on OS/infra defaults. **Method:** for each table, the actual uniqueness/versioning constraint was read directly from `app/db/models.py` (not inferred from docstrings alone) to determine the true growth driver, then cross-referenced against the actual rate-limit/per-cycle caps in `app/core/config.py` and `app/security/rate_limit.py` that bound how fast each driver can fire.

| `gmail_permanent_skips` | One row per permanently-unparseable/oversized IMAP UID | Bounded by how often malformed/oversized messages actually appear (expected to be rare) | **BOUNDED NATURALLY**, low volume expected in practice |
| `telegram_digest_deliveries` | One row per `(account_key, digest_date)` (`UNIQUE`, verified) | At most 1/day/account by construction | **BOUNDED NATURALLY**, slowest grower of any table inventoried |
| `job_reference_tokens` | Delete+reinsert re-sync on every `upsert_job` call — the ONE table with real DELETE logic | Tied 1:1 to `jobs`' own row count and each job's token count | **BOUNDED NATURALLY**, not a growth vector — self-correcting by design |
| `xing_scan_progress` / `automation_schedules` | One row per `(source, mailbox_scope)` / per account | Effectively static, bounded by mailbox/account count | **BOUNDED NATURALLY** |

**Honest summary:** most tables are correctly "APPEND-ONLY INTENTIONAL" by deliberate audit-trail design, and several are genuinely "BOUNDED NATURALLY" with no practical concern. But at least **five tables** (`gmail_message_analyses`, `response_drafts`, `follow_up_proposals`, `candidate_job_matches`, `candidate_cv_drafts`) share a real, previously-uncharacterized **growth-amplification pattern**: because their uniqueness/dedup identity includes `candidate_profile_version`, a single candidate-profile edit does not itself insert new rows, but it invalidates the "reuse an existing row" fast path for every job/message/proposal that gets touched again afterward — so a user who edits their profile repeatedly while iterating on it, combined with an active automation cycle re-processing the same jobs/messages/threads on every interval, could accumulate meaningfully more rows than a naive "one row per real-world job/email" mental model would suggest. This is not a bug (the versioning exists specifically so past drafts/matches/analyses remain auditable against the exact inputs that produced them) and is not fixed or flagged as a finding requiring action — it is exactly the kind of capacity-planning-relevant fact this section exists to surface honestly rather than wave away as "intentional, therefore fine."
